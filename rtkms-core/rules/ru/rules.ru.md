# Правила работы с проектом

## Общие принципы
1. Все артефакты хранятся в виде текстовых файлов Markdown
2. Система разделена на логические модули (требования, задачи, знания, код, документация)
3. Между требованиями, задачами и знаниями поддерживается трассируемость
4. Документация и код, которые создаются ИИ ассистентом должны быть простыми для использования и понимания

## Структура директорий
- `rtkms/docs/requirements/` - содержит все требования проекта
- `rtkms/docs/tasks/` - содержит все задачи проекта
- `rtkms/docs/knowledge/` - содержит все знания проекта
- `rtkms/docs/code/` - содержит документацию кода и диаграммы
- `rtkms/meta/` - содержит метаданные проекта
- `rtkms/rules/` - содержит правила использования системы
- `rtkms/templates/` - содержит шаблоны для создания новых документов
- `rtkms/utils/` - содержит утилитарные скрипты
- `rtkms/_processed/` - содержит обработанные документы
- `src/` - содержит исходный код или тексты, которые создаются в рамках проекта ИИ ассистентом

## Правила именования файлов
- **Требования**: `REQ-{категория}-{номер}.md` (например, REQ-SYS-0001.md)
- **Задачи**: `TASK-{этап}-{номер}.md` (например, TASK-S01-0001.md)
- **Знания**: `KN-{номер}.md` (например, KN-0001.md)

## Правила создания документов

1. **Требования**:
   - Должны иметь уникальный идентификатор
   - Должны быть категоризированы (SYS, FUNC, UI и т.д.)
   - Должны включать критерии приемки

2. **Задачи**:
   - Должны ссылаться как минимум на одно требование
   - Должны иметь статус (backlog, in_progress и т.д.)
   - Должны быть привязаны к этапу проекта

3. **Знания**:
   - Должны быть категоризированы по типу
   - Должны иметь релевантные теги
   - Должны ссылаться на связанные требования или задачи

## Связывание документов
Документы должны быть связаны с использованием markdown-ссылок:
- `[REQ-SYS-0001](../requirements/SYS/REQ-SYS-0001.md)`
- `[TASK-S01-0001](../tasks/in_progress/TASK-S01-0001.md)`
- `[KN-0001](../knowledge/CONCEPT/KN-0001.md)`

## Рабочий процесс
1. Создание требований на основе потребностей проекта
2. Создание задач для реализации требований
3. Создание документов знаний по мере необходимости
4. Обновление статусов документов по мере продвижения работы
5. Связывание документов для поддержания трассируемости

## Обязательные правила
1. ВСЕГДА работать на максимальной производительности, предлагать лучшие решения
2. ВСЕГДА сохранять файлы в правильном формате и по правильному пути
3. ВСЕГДА следовать шаблонам документов из папки templates
4. ВСЕГДА применять правильные именования файлов согласно стандартам:
   - Требования: REQ-{категория}-{номер}.md (пример: REQ-SYS-0001.md)
   - Задачи: TASK-{этап}-{номер}.md (пример: TASK-S01-0001.md)
   - Знания: KN-{номер}.md (пример: KN-0001.md)
   - Документация кода: CD-{имя_файла}.md
   - Диаграммы: {тип_диаграммы}-{имя}.puml
5. ВСЕГДА размещать файлы по указанным путям:
   - Требования: ${requirements_path}/{категория}/REQ-{категория}-{номер}.md
   - Задачи: ${tasks_path}/{статус}/TASK-{этап}-{номер}.md
   - Знания: ${knowledge_path}/{категория}/KN-{номер}.md
   - Документация кода: ${code_docs_path}/CD-{имя_файла}.md
   - Диаграммы: ${code_docs_path}/diagrams/{тип_диаграммы}/{тип_диаграммы}-{имя}.puml
   - Исходный код: ${sources_path}
6. При изменении документа ВСЕГДА проверять и обновлять связи с другими документами
7. ВСЕГДА обновлять статус задач при внесении изменений и переносить файлы в соответствующие каталоги
8. При создании новых документов ВСЕГДА проверять наличие связанных документов
9. Все даты должны быть в формате ГГГГ-ММ-ДД
10. ВСЕГДА сохранять минимализм и лаконичность в документах
11. При удалении или архивации документа ВСЕГДА проверять и исправлять ссылки в других документах
12. ВСЕГДА обновлять индексные файлы при добавлении, изменении или удалении документов
13. Документация кода НЕ ДОЛЖНА дублировать сам код, а должна объяснять его назначение и принцип работы
14. ВСЕГДА проверять файлы документации PlantUML через validate_puml.sh перед их размещением

## Рекомендуемые правила
1. Поддерживать краткость описаний (не более 3-5 предложений)
2. Избегать дублирования информации между документами
3. При создании документов предлагать связать их с существующими
4. Предлагать обновить связанные документы при значительных изменениях
5. Использовать списки вместо длинных параграфов текста
6. Использовать краткие, но информативные заголовки
7. Использовать идентификаторы для четкой ссылки на другие документы
8. Группировать связанные задачи по этапам и статусам
9. Периодически анализировать и архивировать устаревшие документы в _processed
10. Использовать диаграммы для визуализации сложных концепций
11. При изменении файлов изменяется только то, что просит пользователь без внесения корректировок, которые могу вызвать кардинальное изменение контента или галлюцинации.

## Правила обработки файлов
1. Файлы, которые были обработаны и больше не нужны, должны быть перемещены в папку _processed
2. При обработке файлов необходимо сохранять оригинальные имена и добавлять префикс даты YYYYMMDD_
3. Если файл обрабатывается частично, ясно указывать в документации, какие части были обработаны
4. Регулярно проверять проект на наличие "мертвых" ссылок и удаленных документов

## Правила взаимодействия с пользователем
1. При выполнении критических операций (удаление, массовое изменение) ВСЕГДА запрашивать подтверждение
2. Предлагать варианты решения, когда требуется выбор пользователя
3. Уважать настройки интерактивности из конфигурационного файла
4. При неоднозначности в процессе выполнения задачи запрашивать уточнение у пользователя
5. После выполнения сложных операций предоставлять краткую сводку о выполненных действиях
